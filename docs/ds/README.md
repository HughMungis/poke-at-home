## How to read this critically

These documents were generated by an LLM using this repository’s real source as the intended reference. They have not been verified against a running DS emulator. The feasibility document reports that its repository reads failed; the reads for this index also failed, so `docs/DISTRIBUTED.md` could not be checked. This is not a completed source audit.

Check these claims first:

- **Throughput:** establish what the supplied 38× realtime Game Boy baseline measures. Benchmark the complete DS environment and policy loop on the intended two-core ARM machine. The 2× and 5× DS examples are calculations, not measurements.
- **Backend support:** verify installation on ARM, exact frame stepping, framebuffer layout, memory access, save-state restoration, and isolation between worker processes.
- **RAM interpretation:** check every required signal against the exact ROM revision and visible game state. Named source fields do not establish stable addresses; pointers, encryption, and context changes may require decoders.
- **Observation cost:** the 4.27× pixel ratio compares native screens. It does not measure this project’s preprocessing, training memory, or sample throughput.
- **Repository fit:** trace the actual PyBoy dependencies, reset behavior, observation shapes, and worker assumptions before treating the proposed seam as sufficient.
- **Task coverage:** verify that the chosen controls, screens, and progression signals cover the whole initial task. A public decompilation does not establish that those signals are ready to use.

Read the feasibility document first. A decision to build needs measured throughput and validated instrumentation for one ROM revision. Neither exists here.
