- **`red_gym_env_v2.py:290–298, 333, 874–876, 909–921` — The resumed-save misnumbering is real when reset does not adopt.** With `init_state` containing flags 1–8, an empty swarm directory, and no adoption, reset sets `base_required_flags=8` but `swarm_loaded_stage=0`. Setting flag 9 publishes the absolute-stage-9 state as `stage_1.state`. Adopting that file and setting flag 10 then publishes `stage_2.state`, propagating the eight-stage offset. Such a directly accumulated ladder mislabels advanced starts as early segments and orders them incorrectly against correctly numbered states. However, the `stage <= best` guard prevents overwriting an existing stage 1; a correctly numbered frontier can instead suppress these publications. Reimporting through `make_ladder.classify()` recomputes stage from flags rather than preserving the erroneous source filename.

- **`red_gym_env_v2.py:899, 916–921`; `make_ladder.py:91–100` — Adopted ladder stages and published progress use incompatible measurements.** The importer uses the highest set flag index, while publication adds a change in flag count. For example, adopt `stage_7_001.state` containing flags `{1,2,3,4,5,7}`: the loaded stage is 7 and baseline count is 6. If flag 9 becomes set while flag 8 remains unset, publication writes `stage_8.state`, although the importer would classify that same state as stage 9. Conversely, setting a missing earlier flag increases the published stage without advancing the deepest milestone. This corrupts frontier ordering even when adoption loaded a correctly classified file.

- **`red_gym_env_v2.py:333, 912–922` — Clearing required flags hides subsequent progress; the ratchet only prevents reward decreases.** Adopt stage 8 with eight required flags set. A scene clears two of those flags, then the agent sets flag 9: the count is now 7, so `cur=max(7-8,0)=0`. There is neither required-event reward nor publication of the stage-9 breakthrough. Setting flag 10 brings the count to 8 and still produces neither. Thus the explicitly documented flag clearing can prevent newly completed ladder segments from being shared.

- **`red_gym_env_v2.py:819–852, 895–910` — An unreadable frontier file permanently blocks replacement and lower-stage discoveries.** Suppose the directory contains a truncated `stage_12.state` and a valid `stage_8.state`. Adoption catches the stage-12 load failure and falls back to stage 8, but `_swarm_best()` still returns 12 based solely on the filename. Workers subsequently reaching stages 9–12 cannot publish, including a valid replacement for the broken stage-12 file. The supposedly tolerated bad file therefore disables frontier repair and sharing until a worker exceeds stage 12 or someone removes it.
