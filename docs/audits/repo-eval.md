- **eval_checkpoint.py:387–392, 653–654 — Scores identify filenames, not checkpoint contents.** Evaluate `candidates/poke_1000000_steps.zip` containing model A, then replace it with model B from a restarted training run. A’s results still identify B’s filename, and `--until-runs` counts them toward B’s eligibility. Different files with the same basename in `candidates/` and `runs/` also have their scores merged under one identity.

- **eval_checkpoint.py:267, 395–402, 474–475 — A step-capped smoke test is recorded as an hour-long evaluation.** Run `--minutes 60 --steps 1 --runs 5` without `--exact-steps`. Each run performs one action, but the entry records `budget_min: 60`; `pooled_runs(60)` counts all five as qualifying runs. These scores enter the same pool as actual hour-long evaluations.

- **eval_checkpoint.py:613–618; gamereg.py:55–59, 64–86 — Evaluation never verifies the ROM against the reference hash.** Replace `repo/PokemonRed.gb` with a loadable modified ROM that changes encounters while retaining compatible observations and save-state layout. `available()` passes, evaluation uses the modified game, and results are stored as ordinary `"game": "red"` scores alongside reference-ROM results. The promised startup rejection in `verify_rom()` never executes.

- **eval_checkpoint.py:243–248, 329–341 — The seeded random baseline is not reproducible.** `_RandomPolicy` samples an action space belonging to a separate, already-closed environment. Neither global RNG seeding nor resetting the episode environment seeds that space’s independent RNG. Two executions of `--random --exact-steps --steps 10000 --seed 42` can therefore produce different action sequences and scores despite recording the same seed.

- **eval_checkpoint.py:260–290, 297 — Episode resets combine incompatible metric histories and can erase achieved progress.** If a run reaches stage 9 and then truncates, line 290 resets the environment but retains `ever`. Ending immediately afterward records stage 9 from the previous episode alongside badges, maps, and tiles from the fresh initial state. A step-exact run reaching the configured environment limit of `2**23` steps can hit this boundary precisely.

- **eval_checkpoint.py:414–424 — Concurrent result writers lose scores and race over the same temporary file.** Processes A and B both read history `H`. A writes and replaces the results with `H + [A]`; B subsequently writes its previously computed `H + [B]`, deleting A’s result. If both open `RESULTS + ".tmp"` before either replacement, they also share and truncate the same temporary file, and one replacement can fail because the other already moved it.

- **eval_checkpoint.py:415–424 — A history read error silently destroys existing results.** If the results file contains a truncated JSON document, `json.load()` raises and the handler substitutes `[]`. The next successful evaluation replaces the entire historical file with only the new entry, discarding all earlier scores instead of preserving the damaged history for recovery.
